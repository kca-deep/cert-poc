# 법령 대조 검증(RAG) 방안 제안

> 문제지에 인용된 법·시행령·행정규칙 조문이 **현행 규정과 일치하는지 대조 검증**하여
> 오류를 탐지하기 위한 내부 RAG 설계서. (PoC → 폐쇄망 프로덕션)

## 1. 목적과 제약

- **목적**: 문항에 **언급된 사항만** 대상으로, 인용된 조문을 정본(canonical text)과
  대조하여 오류를 탐지한다.
- **검출 대상 오류 패턴**
  1. 존재하지 않는 조문
  2. 개정으로 삭제·이동된 조문
  3. 조문은 맞으나 내용/수치/요건이 다름
  4. 법령명–조문 불일치(엉뚱한 법)
  5. 최신 개정 미반영
- **제약**
  - **폐쇄망(내부망) 프로덕션** → 외부 API(국가법령정보 OpenAPI, 외부 임베딩/LLM) 런타임 호출 불가. 전부 로컬.
  - **개정 시 수동 업데이트** → 법령 코퍼스는 사람이 관리하는 *버전드 데이터셋*. 감사·롤백이 쉬워야 함.
  - 기존 스택(`src/core` 파이프라인 + per-type LLM + SQLite)과 정합해야 함.

## 2. 핵심 통찰 — 전형적 RAG가 아니다 → 벡터DB 불필요

이 문제의 본질은 *대규모 비정형 문서의 의미검색*이 아니라
**조문 키(법령명 + 조·항·호)로의 결정적 lookup + 텍스트 대조**다.

| 일반 RAG | 본 과제 |
|---|---|
| 대규모·비정형 코퍼스 | 작고 **구조적**(도메인 법령 수십 개 ≈ 수천~수만 조문) |
| 임의 토큰 청킹 필요 | **조(Article) 단위가 자연 청크** — 청킹 난제 거의 없음 |
| 의미검색이 1차 | **키 기반 결정적 조회가 1차**, 의미검색은 보조 리콜 |
| 검색 인프라가 핵심 | **저장 포맷·버전 관리·근거 추적**이 핵심 |

→ 수만 청크 규모에서는 전용 벡터DB(Chroma/Qdrant/FAISS)가 **과투자**다.
brute-force cosine으로도 ms 단위이며, 폐쇄망 반입·운영 부담만 늘린다.

## 3. 권고 아키텍처 — SQLite(FTS5) 단일 파일 코퍼스

이미 `api/db.py`가 SQLite를 사용 → **의존성 0, 폐쇄망 반입 이슈 0, 스택 일관성**.

### 3.1 검색 전략 (단계적 폴백)

| 단계 | 방식 | 역할 |
|---|---|---|
| 1차 | `WHERE law_id=? AND article_no=?` | 조번호 있는 인용 → 결정적 1건 조회 |
| 2차 | FTS5 BM25 (한국어 n-gram 토크나이저) | 의역·조번호 없는 인용 → 후보 top-k 회수 |
| 3차 (선택) | 로컬 임베딩 cosine (numpy) | 리콜 부족이 **측정되면** 추가 (YAGNI) |

> **확장 경로**: 의미검색이 꼭 필요해지면 임베딩은 기존 llama.cpp(`:8080`)에
> `/v1/embeddings`(예: bge-m3·ko-sroberta GGUF/ONNX 반입)를 띄워 **신규 인프라 없이**
> 처리. 한 파일 내 하이브리드가 필요하면 `sqlite-vec` 확장으로 확장.

### 3.2 코퍼스 데이터 모델

법령은 계층 트리(법 > 편/장/절 > 조 > 항 > 호 > 목). 청크 = **조(또는 항)** 단위.

- **article 테이블(청크)**: `law_id, article_no, paragraph_no, item_no, 계층경로, 원문(text)`
- **메타**: `law_name(정식), law_type(법률/시행령/시행규칙/행정규칙), effective_date(시행일자),
  공포번호, is_current`
- **alias 테이블**: 약칭·띄어쓰기 변형 → 정식 법령명 매핑
  (예: `개인정보보호법` → `개인정보 보호법`, `정보통신망법` → 정식명)
- **manifest 테이블**: 법령별 최신 여부·마지막 갱신일·출처 → 검수자가 코퍼스 기준 시점 확인
- **FTS5 가상 테이블**: article 원문 인덱싱(BM25). 한국어는 기본 토크나이저가 약하므로
  유니그램/트라이그램(n-gram) 토크나이저 적용.

### 3.3 버전 관리 (중요)

개정 시 기존 레코드를 **덮어쓰지 않는다**. `effective_date`·공포번호 단위로 **신규 버전을
적재**하고 `is_current` 플래그만 전환한다.

- "문제지가 어느 시점 기준인지" 검증 가능
- 과거 시험지 재검증, 감사, 롤백 가능

## 4. 검출 파이프라인 (기존 per-type LLM 패턴에 통합)

법령 도메인 그룹(G4: A09/A20) 옆에 검출기 하나로 통합한다. 흐름:

1. **추출(Extract)**: 문항 → `{법령명, 조, 항호, 인용문}` JSON (정규식 + LLM 혼합)
2. **정규화(Resolve)**: alias 테이블로 정식 법령명 변환 → 조문 키 생성
3. **회수(Retrieve)**: 3.1의 1~3차 검색으로 정본 조문(+시행일자) 확보
4. **대조·판정(Judge)**: 정본 텍스트를 컨텍스트로 LLM에 주고 일치 여부를 `issues[]`로 출력
   — **기존 `prompts/_shared/output_schema.json` 재사용**
5. **근거 첨부**: 판정에 사용한 조문(법령명·조번호·**시행일자**)을 필수 인용 → 검수자 클릭 확인

이는 기존 per-type LLM 패턴(프롬프트 + 컨텍스트 주입 + JSON 판정)과 동일한 모양이라
파이프라인 통합이 자연스럽다.

## 5. 수동 업데이트(개정 대응) 워크플로 — 운영 핵심

```
외부망 다운로드 → 폐쇄망 반입 → ingest CLI 실행 → 진단 검수 → is_current 전환
```

- **원본 포맷**: 가능하면 법제처 법령 **XML**(구조 명확). 불가 시 기존 `hwp_parser`/kordoc로
  HWP→MD 변환 후 조문 파서 적용.
- **조문 파서**: `제N조(제목) 본문 / ①②③ 항 / 1.2.3. 호` 패턴을 정규식으로 분해해
  article 레코드 생성(한국 법령은 형식이 표준화돼 파싱 난도 낮음).
- **ingest CLI 예시**:
  ```
  python -m ingest_law --file 개인정보보호법_20240315.xml --effective 2024-03-15
  ```
  적재 후 **추가/변경/삭제 조문 수 + 파싱 실패 조문** 진단 리포트 출력 → 담당자 검수.
- **코퍼스 스냅샷**: 날짜 태그로 보관(SQL dump 또는 별도 디렉터리) → 이력 추적·감사.

## 6. 리스크 및 주의사항

- **환각 차단**: 프롬프트에 "**제공된 조문 텍스트에만 근거**하라, 조문이 없으면 '판정불가'"
  강제 + 근거 조문 인용 필수.
- **코퍼스 미비**: 인용 법령이 코퍼스에 없으면 **조용히 통과 금지** → "해당 법령 없음"을
  명시적 상태로 반환.
- **추출 누락**: 조번호 없는 인용("위 법령에 따르면...")은 회수 실패 가능 → confidence를
  낮춰 "확인필요"로 표시.
- **약칭/띄어쓰기 변형**: alias 사전을 지속 관리.

## 7. 개발 보조 vs 프로덕션 구분 (명시)

- 개발 세션에 연결된 `mcp__korean-law`(`get_law_text`, `search_law`, `verify_citations` 등)는
  **개발·평가셋 구축 단계의 정본 수집/검증**에만 사용한다.
- **폐쇄망 프로덕션 런타임에서는 사용 불가**(외부 의존성). 프로덕션은 **로컬 적재 코퍼스를
  단일 소스**로 삼는다.

## 8. 결론 (한 줄)

벡터DB 대신 **SQLite + FTS5 버전드 코퍼스 + 결정적 키 lookup**(+ 필요 시 로컬 임베딩
하이브리드)이 이 과제(작고 구조적인 코퍼스, 폐쇄망, 수동 개정, 정확 대조)에 가장 적합하며
기존 스택에 그대로 얹힌다.
